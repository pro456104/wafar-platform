# Accessibility and Interaction-State Checklist: File Intake (R2)

**Purpose**: Requirements-quality review of the intake's accessible behaviour — where focus moves as the page's states replace one another, what assistive technology is told and when, how the page and the shared shell are operated without a pointer, how names, reading order, and language survive truncation and mixed direction, which target, motion, and reflow bounds apply, and how the scan and the keyboard-only pass measure all of it.
**Created**: 2026-11-17
**Feature**: [spec.md](../spec.md)
**Scope**: The page's eight states and the eleven presentations the contract measures, plus the R1 shell surfaces this slice renders for the first time (FR-051 – FR-060). Copy correctness, format inspection, performance, and security are the sibling checklists' subjects and are not repeated here.

**Note**: This custom checklist is generated by the `/speckit.checklist` command based on feature context and requirements.
**Review Ownership**: This checklist is a reviewer-owned requirements-quality review artifact. Mark an item `[x]` only when the reviewer determines the requirements-quality criterion is satisfied.
**Marker Semantics**: `[x]` means the criterion has been reviewed and satisfied for requirements quality. It does not mean implementation work is complete.

## Focus Movement Across States

- [ ] CHK001 - Is a focus destination fixed for every one of the eleven presentations — the choosing control, the selected card, the two progress phases, the three outcomes, and the quota block's exceeded, loading, and read-failure presentations — and not only for an outcome's action? [Completeness, Spec §FR-006, §AC-045; Contract §3]
- [ ] CHK002 - Is the account menu's focus behaviour specified — where focus lands when it opens, whether it is contained while open, and where it returns on each dismissal — as the drawer's is? [Consistency, Spec §FR-051 vs §FR-053, §AC-035 vs §AC-037]
- [ ] CHK003 - Is the sign-out confirmation specified as a modal surface — where focus lands when it opens, whether Escape cancels it, and where focus returns on cancel — or is only its effect on the session stated? [Gap, Spec §FR-051, §AC-036]
- [ ] CHK004 - Is the bottom bar's hide-on-scroll specified for the case where the raised search action holds keyboard focus as the bar hides, given that the action must leave the focus order and the accessibility tree while hidden? [Edge Case, Gap, Spec §FR-054, §AC-039]
- [ ] CHK005 - Is the focus destination after «إلغاء» and after a departure returns the page to its choosing state stated, rather than inferred from the general "first action" rule? [Clarity, Spec §FR-048, §FR-050, §AC-010]
- [ ] CHK006 - When a successful re-read restores the upload control or an outcome's withheld action, is the focus consequence fixed — whether focus stays on «تحديث» or moves to the restored control? [Gap, Spec §FR-015, §FR-017]
- [ ] CHK007 - Is the quota-exceeded state's focus behaviour distinguished between its on-load appearance and its appearance after a refusal removes the in-flight block, so that the «الحصة» heading receives focus only in the second case? [Consistency, Spec §FR-017; Contract §3 row 8]
- [ ] CHK008 - Does the rule that focus never remains on a removed control cover every removal path — cancel, outcome replacement, quota withholding, session end, and the reload that discards the held file? [Coverage, Spec §FR-006, §FR-004, §FR-061, §AC-045]

## Announcements and Assistive-Technology State Exposure

- [ ] CHK009 - Is every change of state a sighted merchant would perceive required to be announced, across all eleven presentations, rather than only the progress state's start, cancellation, and outcome? [Completeness, Constitution Principle IV; Spec §FR-048, §AC-045]
- [ ] CHK010 - Does the ownership rule name the announcements explicitly among the text the contract owns, so each of the page's messages has exactly one owner and no announcement is left to be inferred from a visible string? [Traceability, Spec §FR-065, §FR-063; Contract §7]
- [ ] CHK011 - Is "one live region per page" coherent with a politeness mapping that assigns both polite and assertive announcements to that one region? [Conflict, Contract §7; Spec §FR-065]

- [ ] CHK013 - Are the announcement boundaries quantified — once per phase and per outcome, never per percentage, no repeat while the same state stays on screen, and no second announcement when the screening outlasts a minute? [Clarity, Spec §FR-048, §AC-003; Contract §7]
- [ ] CHK014 - Are the quota block's loading, settled, exhausted, and read-failure presentations required to expose their state to assistive technology, and not only to the eye? [Coverage, Constitution Principle IV; Spec §FR-015, §FR-017; Contract §3 rows 8 – 10]
- [ ] CHK015 - Is the quota update that follows every settled outcome required to be announced, with a politeness and a once-per-change rule that a count changing across several consecutive outcomes can satisfy? [Gap, Spec §FR-015, §AC-034; Contract §7]
